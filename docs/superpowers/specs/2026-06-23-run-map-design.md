# Run Map (Branching Graph) — Design

**Date:** 2026-06-23
**Status:** Approved design, pre-implementation
**Scope:** Replace the linear `stage`-based run progression with a branching column/row graph (Slay-the-Spire style). Generate it deterministically from the seed. Only `battle`/`elite`/`boss` node types are active; `relic`/`event`/`shop` stay enum-only for future specs. Relic rewards remain post-battle (current flow preserved).

---

## 1. Motivation

The run is currently linear: `RunState.stage` counts 0..`enemyCount`(5), then a boss. After 4-5 runs this is repetitive. The brief asked for a Slay-the-Spire branching map to raise replayability: the player picks a path through a graph of nodes, paths diverge and reconverge, the boss is the final node.

The data shape already exists (inert) from the Event Bus milestone:
```ts
export type RunNodeType = 'battle' | 'elite' | 'boss' | 'event' | 'shop' | 'relic'
export interface RunNode { id: string; type: RunNodeType; next: string[] }
export interface RunState { /* ... */ map?: RunNode[]; currentNodeId?: string }
```
This spec populates `map`/`currentNodeId` and rewires progression to walk the graph instead of incrementing `stage`.

## 2. Decisions (locked in brainstorming)

- **Graph form:** columns/rows (floors). Floor 0 = single start; floor N-1 = single boss; middle floors have 2-3 nodes with edges only to adjacent-floor nodes. Paths diverge and reconverge.
- **Active node types:** `battle`, `elite`, `boss` only. `relic`/`event`/`shop` remain in the enum but are NEVER generated by this spec.
- **Relics:** unchanged — chosen post-battle via the existing `chooseRelic` flow. No `relic` map node.
- **Determinism:** generated once, from a dedicated RNG channel `mapRngChannel = 4`, at `confirmTeam` (when the run truly begins, after the draft). Same seed → same map.
- **Difficulty:** a node's **floor depth** replaces `stage` as the input to enemy budget scaling. `elite` nodes get a budget bump.
- **All tunables live in `BALANCE.map`** so balance can change without touching logic.

## 3. Architecture

### 3.1 Constants (`data/constants.ts`)

Add a `map` block to `BALANCE`:

```ts
map: {
  floors: 6,            // total floors incl. start(0) and boss(last). 4 "middle" battle floors.
  minWidth: 2,          // min nodes per middle floor
  maxWidth: 3,          // max nodes per middle floor
  eliteFloors: [3],     // floor indices (0-based) that are forced elite. Must be a middle floor.
  eliteBudgetMult: 1.35,// enemy budget multiplier for elite nodes
} as const
```

`enemyCount` (5) is no longer the progression driver but stays for the budget formula's base; the map's middle-floor count is the new "how many fights". (See §3.4 — budget keys off floor depth, not `enemyCount`.)

### 3.2 Map generation (`game/engine/map.ts` — new)

Pure function, deterministic from an `Rng`:

```ts
export const mapRngChannel = 4

export function generateMap(rng: Rng): RunNode[]
```

Algorithm:
1. Floor 0: one `battle` node (`id = 'f0n0'`). The run's entry — `currentNodeId` starts here.
2. Floors 1..floors-2 (middle): each floor gets `rng.int(minWidth, maxWidth)` nodes, `id = 'f{floor}n{i}'`. Type is `elite` if the floor is in `eliteFloors`, else `battle`.
3. Final floor (`floors-1`): one `boss` node (`id = 'f{last}n0'`).
4. Edges: for each node on floor `f`, connect to 1-2 nodes on floor `f+1` such that **every** next-floor node is reachable from at least one current-floor node (no orphans) and every current node has at least one outgoing edge. Concretely: sort next-floor nodes by index; assign edges so coverage holds, then add a deterministic extra edge per node where width allows. The boss floor has one node, so all penultimate-floor nodes point to it.

Node `id` is the stable key used by `currentNodeId` and `next[]`.

**Determinism:** all randomness via the passed `rng` (forked from `mapRngChannel`). No `Date.now`/`Math.random`.

### 3.3 Run engine wiring (`game/engine/run.ts`)

- `confirmTeam(state, team)` additionally generates the map and sets `currentNodeId` to the floor-0 node:
  ```ts
  const map = generateMap(createRng(state.seed).fork(mapRngChannel))
  return { ...state, team, activeSynergies: detectSynergies(team), phase: 'team', map, currentNodeId: map[0]!.id }
  ```
- New helper `nodeById(state, id): RunNode | undefined` and `nodeDepth(state, id): number` (parse floor from id, or store depth on the node — see §6 open decision resolved: depth is parsed from the `f{n}` id prefix; helper centralizes it so the id format is encapsulated).
- `nextBattle` keys difficulty off the **current node's depth**, not `state.stage`. `isBoss` becomes `currentNode.type === 'boss'`. Elite nodes pass `eliteBudgetMult` into the enemy budget. `budgetForStage(depth)` is reused with `depth` in place of `stage`.
- `advanceToNode(state, nodeId): RunState` — validates `nodeId ∈ currentNode.next`, sets `currentNodeId = nodeId`. Throws on an illegal move (defensive; UI only offers legal nodes).
- `stage` is retained as a derived/legacy field for any code still reading it (e.g. relic-offer RNG fork uses `run.stage` — keep it as "number of battles won so far" so relic offers stay deterministic and varied). Increment it on each battle resolution as today.

### 3.4 Difficulty by depth

Today: `budgetForStage(state.stage)`. New: `budgetForStage(nodeDepth(currentNode))`, with elite multiplier:
```ts
const depth = nodeDepth(state, state.currentNodeId!)
const isElite = currentNode.type === 'elite'
const budget = budgetForStage(depth) * (isElite ? BALANCE.map.eliteBudgetMult : 1)
```
Boss uses the existing `generateBossTeam` path. Depth 0 = easiest, penultimate floor = hardest pre-boss, matching the old linear curve since floors ≈ old stages.

### 3.5 UI (`hooks/useRun.ts` + new `components/screens/MapScreen.tsx`)

- `useRun` gains `view: 'map'` and a `chooseNode(nodeId)` action. New flow:
  ```
  team → map → battle → (replay) → victory → relic-choice → map → … → boss → win/defeat
  ```
  After `chooseRelic`, instead of auto-starting the next battle, return to `'map'` showing the now-reachable nodes from the current node. The boss node, when chosen, runs the boss battle then → `win`/`defeat`.
- `chooseNode(nodeId)` calls `advanceToNode` then `startBattle()` (which uses the new node-depth difficulty). `'map'` view highlights `currentNode.next` as the only selectable nodes; already-passed nodes shown as visited.
- `MapScreen` renders floors bottom-to-top (or left-to-right), nodes as buttons with a type icon (battle/elite/boss), edges as connecting lines, current position highlighted, reachable nodes enabled, others disabled. Keep it simple: a CSS grid of floors with absolutely-positioned edge lines, or a minimal SVG. Visual polish is secondary to correct reachability.
- `CampaignRunner.tsx` adds the `'map'` case to its view switch and crossfade keying.
- `battleNumber`/`bossNext`/`enemyCount` in `RunController` are recomputed from the graph: `bossNext = currentNode.type === 'boss'`; `battleNumber` = depth+1; `enemyCount` = number of middle floors (for the "X di Y" label).

## 4. Data flow

```
confirmTeam ─generates─> map + currentNodeId(f0n0)
   │
useRun(view='team') ──> 'map' (show f0n0 as start / its next)
   │ chooseNode(id)
   ├─> advanceToNode ─> startBattle (depth-scaled enemy) ─> 'battle'
   │      └─ replay ─> revealResult ─> 'victory'|'defeat'
   │ advance ─> 'relic-choice' ─> chooseRelic ─> back to 'map'
   └─ (repeat until a 'boss' node is chosen) ─> 'win'|'defeat'
```

## 5. Testing

- **map.test.ts** (new): `generateMap` —
  - Determinism: same seed → identical node array (deep-equal).
  - Structure: floor 0 single battle; last floor single boss; middle floors width ∈ [minWidth,maxWidth]; elite floors typed `elite`.
  - **Connectivity (the key invariant):** every non-start node is reachable from `map[0]` via `next` edges; no node (except boss) has empty `next`; no edge crosses non-adjacent floors. A graph-traversal test asserting full reachability.
  - Id format `f{floor}n{index}` parseable by `nodeDepth`.
- **run.test.ts** (extend): `confirmTeam` populates `map`/`currentNodeId`; `advanceToNode` accepts a legal next node and rejects an illegal one (throws); `nextBattle` scales difficulty by node depth (elite node yields higher budget than a battle node at the same depth); boss node sets `isBoss`.
- **Determinism regression:** existing campaign/relic tests must stay green. `run.stage` semantics preserved enough that `relicOffer` RNG forks still produce stable offers (test: relic choices unchanged for a fixed seed across N wins).
- **No UI snapshot tests required** (MapScreen is presentational); a light render-smoke test optional.

## 6. Out of scope (explicit)

- `event`/`shop`/`relic` node generation and gameplay (separate specs).
- Map-node rewards beyond the existing post-battle relic choice.
- Multiple acts/biomes, map regeneration mid-run, branching boss selection.
- Visual polish / animations on the map beyond basic readable layout.
- Balancing the floor counts / elite placement to a target win-rate (defaults in `BALANCE.map`; tune after playtesting).

## 7. Risks

- **Connectivity bugs** (orphan node, dead-end mid-graph) would soft-lock a run. Mitigation: the reachability + no-empty-`next` test in §5 is the gate; `advanceToNode` validates moves defensively.
- **`stage` dual meaning.** Keeping `stage` as "battles won" while depth drives difficulty risks confusion. Mitigation: a single helper `nodeDepth` owns difficulty input; `stage` is documented as "wins so far, for relic-offer variety only".
- **Determinism drift** from generating the map at `confirmTeam` if any caller generates twice. Mitigation: generate exactly once in `confirmTeam`; `generateMap` is pure and re-deriving from the same seed is identical anyway.
- **UI flow regressions** (the victory→relic→map loop). Mitigation: `useRun` view-transition coverage; the engine functions are pure and unit-tested independent of React.
